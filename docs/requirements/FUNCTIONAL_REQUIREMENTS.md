# Functional requirements

| ID | Requirement | URS | Design | Tests |
|---|---|---|---|---|
| FRS-BB-001 | Patient identity match at issue requires two tokens that match stored MRN/DOB/name fields (`PatientIdentityMatchRule`). | URS-BB-001 | `IssueGate` `ISS-IDENTITY` | Domain + issue integration |
| FRS-BB-002 | Antibody history is append-only. Add requires `immuno.record`; deactivation requires a reason and `immuno.override` in the Application service. Deactivated rows remain visible and continue to block electronic XM. | URS-BB-002 | `AntibodyHistory`; `ImmunoAuthorizationRule`; `ElectronicCrossmatchEligibilityService` | `ElectronicXmHistoryRegressionTests`; Phase 3 antibody permission tests |
| FRS-BB-003 | Merged patient records HardStop accession, visits, orders, result entry/verify/correct/invalidate, immunohematology writes, special requirements, issue, allocation, compatibility evaluation, and crossmatch (`PAT-MERGED-INACTIVE`). Inactive status is not blocked. Staff with `patient.merge` can merge a duplicate into the survivor (`POST /api/patients/{id}/merge` and ADT A18/A40). Demographic `patient.write` does not grant merge. History is reassigned, not deleted. Discordant ABO/Rh HardStops the merge. | URS-BB-015, URS-BB-017 | `PatientMergeService`; `PatientMergeRule`; patient detail merge UI | `PatientMergeServiceTests`; Phase 8 seed tests; Phase 5 HL7 merge tests; `MergedPatientClinicalUseTests` |
| FRS-BB-010 | Specimen expiration is computed from collection time and alloimmunization-risk policy. Expired or non-accepted specimens HardStop issue, result entry, and result verification. | URS-BB-003, URS-BB-016 | `SpecimenExpirationRule`; `ResultService.ValidateSpecimenForEntryAsync` | Domain expiry boundary; `MergedPatientClinicalUseTests` |
| FRS-BB-020 | Verified results are not overwritten. Corrections create a new version and retain the original. | URS-BB-004 | `ResultService` | Result versioning tests |
| FRS-BB-079 | Result provenance is stored as Manual, Instrument, Interface, or Calculated. Instrument and interface entries start `PendingVerification`. Manual and calculated entries start `Entered` and may be submitted for verification. | URS-BB-047 | `ResultSource`; `ResultLifecycleRule`; `ResultService` | `ResultLifecycleRuleTests`; `ResultLifecycleTests` |
| FRS-BB-077 | Invalidating a result requires `result.invalidate` and a reason. A verified result is superseded by a new Invalidated version; the original row stays Verified. An unverified correction is marked Invalidated and the prior verified row becomes current again (OCD-016). Posted ABO/antibody history is not auto-reverted (OCD-017). | URS-BB-046 | `ResultService.InvalidateResultAsync`; `ResultAuthorizationRule` | `ResultLifecycleTests`; `ResultAuthorizationRuleTests` |
| FRS-BB-021 | Manually recording current ABO/Rh requires `immuno.override` in the Application service (not only the API). Antibody add and antigen-profile writes require `immuno.record`. Antibody deactivate requires `immuno.override`. A reason is required for manual ABO and deactivate. History is append-only. | URS-BB-019, URS-BB-002 | `ImmunohematologyService`; `ImmunoAuthorizationRule` | `ImmunoAuthorizationRuleTests`; Phase 3 immuno permission tests |
| FRS-BB-022 | Patient ABO/Rh verification applies `SelfVerifyRule` when `Result.BlockAboSelfVerify` is on (default). `MarkComplete` does not auto-verify ABO/Rh. Current `PatientBloodTypeHistory` is written only after a successful verify. | URS-BB-020 | `ResultService`; `SelfVerifyRule` | Phase 3 ABO self-verify and MarkComplete tests |
| FRS-BB-023 | Adding a special transfusion requirement requires `immuno.record` in the Application service. Deactivating one requires a reason and `immuno.override`. Callers that skip the API filter cannot change `ISS-SPECIAL-REQ` facts. | URS-BB-021 | `SpecialRequirementService`; `ImmunoAuthorizationRule` | `ImmunoAuthorizationRuleTests`; Phase 3 special-requirement permission test |
| FRS-BB-024 | DIN lookback recall requires `lookback.manage` in the Application service. Each component recall is applied through `InventoryService.RecallForLookbackAsync`; a failed status transition fails the lookback. Selected/Assigned/Allocated/Crossmatched/ReturnPending may move to Recalled. Transfused units are notified, not recalled. | URS-BB-022 | `LookbackService`; `LookbackAuthorizationRule`; `InventoryStatusTransition` | `LookbackAuthorizationRuleTests`; `InventoryStatusTransitionTests`; Compliance lookback tests |
| FRS-BB-030 | Compatibility decisions return structured `RuleResult` codes and messages. The engine never downgrades a HardStop. | URS-BB-005 | `RuleEvaluation` | Aggregation tests |
| FRS-BB-031 | `IssueGate` evaluates identity, specimen, ABO/Rh, allocation, XM, special requirements, appearance, location, emergency ABO, antigen-negative, and autologous/directed rules before issue. | URS-BB-006 | `IssueGate` | `IssueGateSafetyRegressionTests` |
| FRS-BB-032 | Autologous/directed issue to a non-designated patient is HardStop `ISS-AUTO-DIR` inside the issue gate. | URS-BB-008 | `AutologousDirectedRule` | Domain + issue integration |
| FRS-BB-033 | Electronic XM eligibility is an evaluated service (`eligible` + criteria), not a checkbox. Any antibody-history row fails `XM-EC-HISTORY`. | URS-BB-009 | `ElectronicCrossmatchEligibilityService` | Eligibility tests |
| FRS-BB-040 | Emergency/MTP issue is a distinct type. Missing XM becomes an overridable Warning; ABO/identity/status HardStops still apply unless a listed emergency warning conversion exists. Override reason and authorizer are required. Emergency/MTP also requires `issue.emergency-release`. Non-emergency warning overrides require `issue.override`. | URS-BB-006 | `IssuingService`; `IssueAuthorizationRule` | Phase 4 emergency tests; `IssueAuthorizationRuleTests`; Phase 8 seed tests |
| FRS-BB-041 | At most one `Reserved` allocation and one `Issued` issue exist per unit (filtered unique indexes). Concurrent conflicts fail closed. | URS-BB-007 | `IX_Allocations_OneReservedPerUnit`, `IX_Issues_OneOpenIssuePerUnit` | `AllocationIssueConcurrencyTests` |
| FRS-BB-050 | Inventory transitions are allow-listed. Each transition writes `InventoryStatusHistory` + audit. | URS-BB-010 | `InventoryStatusTransition` | Transition tests |
| FRS-BB-051 | Unit ABO/Rh retype is entered, then verified. Status stays Received until verify. Matching verify → Available; mismatch → Quarantine. Default blocks the entering user from verifying (`RES-SELF-VERIFY`, `Inventory.BlockRetypeSelfVerify`). | URS-BB-018 | `ProductRetypeService`; `SelfVerifyRule` | `ProductRetypeServiceTests` |
| FRS-BB-052 | Releasing a unit from quarantine requires `inventory.release` in the Application service (not only the API). Dual-verifier policy still applies. | URS-BB-023 | `InventoryService`; `InventoryAuthorizationRule` | `InventoryAuthorizationRuleTests`; InventoryService permission test |
| FRS-BB-053 | Converting a directed unit to allogeneic inventory requires `inventory.release` in the Application service (not only the API). Reason and dual-verifier policy still apply. | URS-BB-024 | `InventoryService`; `InventoryAuthorizationRule` | `InventoryAuthorizationRuleTests`; InventoryService directed-conversion permission test |
| FRS-BB-054 | Releasing a unit from operational hold requires `inventory.release` in the Application service (not only the API). | URS-BB-025 | `InventoryService`; `InventoryAuthorizationRule` | `InventoryAuthorizationRuleTests`; InventoryService hold-release permission test |
| FRS-BB-055 | Verifying a test result or unit ABO/Rh retype requires `result.verify` in the Application service (not only the API). Self-verify policy still applies. | URS-BB-026 | `ResultService`; `ProductRetypeService`; `ResultAuthorizationRule` | `ResultAuthorizationRuleTests`; Phase 3 and ProductRetype permission tests |
| FRS-BB-056 | Allocating a unit requires `compatibility.allocate` in the Application service. Recording a crossmatch requires `compatibility.crossmatch`. Callers that skip the API filter cannot reserve a unit or record XM used at issue. | URS-BB-027 | `CompatibilityService`; `CompatibilityAuthorizationRule` | `CompatibilityAuthorizationRuleTests`; PatientAllocation permission tests |
| FRS-BB-057 | Issuing a unit requires `issue.create` in the Application service (not only the API). Emergency/MTP still also requires `issue.emergency-release`. | URS-BB-028 | `IssuingService`; `IssueAuthorizationRule` | `IssueAuthorizationRuleTests`; Phase 4 issue-create permission test |
| FRS-BB-058 | Entering a result or unit retype requires `result.enter` in the Application service. Correcting a verified result requires `result.correct` (including save-as-correction). Invalidating a result requires `result.invalidate`. | URS-BB-029, URS-BB-046 | `ResultService`; `ProductRetypeService`; `ResultAuthorizationRule` | `ResultAuthorizationRuleTests`; Phase 3 and ProductRetype permission tests; `ResultLifecycleTests` |
| FRS-BB-059 | Accessioning a specimen requires `specimen.accession` in the Application service. Editing collection metadata requires `specimen.edit`. Rejecting a specimen requires `specimen.reject`. | URS-BB-030 | `SpecimenService`; `SpecimenAuthorizationRule` | `SpecimenAuthorizationRuleTests`; Phase 3 specimen permission tests |
| FRS-BB-061 | Updating patient demographics requires `patient.write` in the Application service (not only the API). ADT inbound still writes through the HL7 processor, not `PatientService`. | URS-BB-031 | `PatientService`; `PatientAuthorizationRule` | `PatientAuthorizationRuleTests`; PatientService permission test |
| FRS-BB-062 | Dividing, pooling, or applying a product modification requires `inventory.modify` in the Application service (not only the API). Result units still land in Quarantine. | URS-BB-032 | `BloodProductModificationService`; `InventoryAuthorizationRule` | `InventoryAuthorizationRuleTests`; BloodProductModificationService permission test |
| FRS-BB-063 | Correcting unit ISBT identity requires `inventory.correct-identity` in the Application service (not only the API). Post-issue corrections remain locked unless the post-event path is used. | URS-BB-033 | `ComponentIdentityCorrectionService`; `InventoryAuthorizationRule` | `InventoryAuthorizationRuleTests`; ComponentIdentityCorrectionService permission test |
| FRS-BB-064 | Releasing an allocation requires `compatibility.allocate` in the Application service (not only the API). Callers that skip the API filter cannot return a reserved unit to Available. | URS-BB-034 | `CompatibilityService`; `CompatibilityAuthorizationRule` | `CompatibilityAuthorizationRuleTests`; PatientAllocation release permission test |
| FRS-BB-065 | Completing an ISBT scan session or creating a manual component requires `inventory.receive` in the Application service (not only the API). Walk-in `InventoryService` receive remains a separate path. | URS-BB-035 | `ScanSessionService`; `ManualComponentEntryService`; `InventoryAuthorizationRule` | `InventoryAuthorizationRuleTests`; ISBT manual-entry permission test |
| FRS-BB-066 | Updating a reaction investigation, recording CBER notification, or recording the written fatality report requires `reaction.investigate` in the Application service. Opening from a suspected transfusion remains an automatic issue-path write. | URS-BB-036 | `ReactionInvestigationService`; `ReactionAuthorizationRule` | `ReactionAuthorizationRuleTests`; ReactionInvestigationService permission test |
| FRS-BB-067 | Walk-in receive, expected-arrival confirmation, and normalized-component intake require `inventory.receive` in `InventoryService` (not only the API). ISBT scan-session complete and manual entry remain separately gated. | URS-BB-037 | `InventoryService`; `InventoryAuthorizationRule` | `InventoryAuthorizationRuleTests`; InventoryService receive permission test |
| FRS-BB-068 | Returning an issued unit to Available, Quarantine, or Discarded requires `issue.return` in the Application service (not only the API). | URS-BB-038 | `IssuingService`; `IssueAuthorizationRule` | `IssueAuthorizationRuleTests`; Issuing return permission test |
| FRS-BB-069 | Documenting a transfusion requires `transfusion.document` in the Application service (not only the API). Callers that skip the API filter cannot mark a unit Transfused. | URS-BB-039 | `IssuingService`; `IssueAuthorizationRule` | `IssueAuthorizationRuleTests`; Issuing transfusion-document permission test |
| FRS-BB-071 | Recording ward receipt of an issued unit requires `transfusion.document` in the Application service (not only the API). Callers that skip the API filter cannot unblock transfusion documentation. | URS-BB-040 | `IssuingService`; `IssueAuthorizationRule` | `IssueAuthorizationRuleTests`; Issuing ward-receipt permission test |
| FRS-BB-072 | Discarding a unit requires `inventory.discard` in the Application service (not only the API). Dual-verifier checks still apply. | URS-BB-041 | `InventoryService`; `InventoryAuthorizationRule` | `InventoryAuthorizationRuleTests`; InventoryService discard permission test |
| FRS-BB-073 | Transferring a unit between locations requires `inventory.transfer` in the Application service (not only the API). | URS-BB-042 | `InventoryService`; `InventoryAuthorizationRule` | `InventoryAuthorizationRuleTests`; InventoryService transfer permission test |
| FRS-BB-074 | Direct inventory recall requires `inventory.recall` in the Application service. Lookback DIN recall remains `lookback.manage` only (OCD-014) via `RecallForLookbackAsync`. | URS-BB-043 | `InventoryService`; `LookbackService`; `InventoryAuthorizationRule` | `InventoryAuthorizationRuleTests`; InventoryService recall permission tests |
| FRS-BB-075 | Creating or updating a quality-system deviation requires `deviation.manage` in the Application service (not only the API). | URS-BB-044 | `DeviationService`; `DeviationAuthorizationRule` | `DeviationAuthorizationRuleTests`; DeviationService permission tests |
| FRS-BB-076 | Creating a patient record requires `patient.write` in `PatientService` (not only the API). ADT inbound still writes through the HL7 processor, not `PatientService`. | URS-BB-045 | `PatientService`; `PatientAuthorizationRule` | `PatientAuthorizationRuleTests`; PatientService create permission test |
| FRS-BB-077 | Saving a unit blood attribute requires `inventory.receive` in `InventoryService` (not only the API). | URS-BB-046 | `InventoryService`; `InventoryAuthorizationRule` | `InventoryAuthorizationRuleTests`; InventoryService attribute permission test |
| FRS-BB-081 | Returning a unit to the supplier requires `inventory.receive` in `InventoryService` (not only the API). | URS-BB-048 | `InventoryService`; `InventoryAuthorizationRule` | `InventoryAuthorizationRuleTests`; InventoryService return-to-supplier permission test |
| FRS-BB-060 | Audit events are append-only and written in the same save pipeline as the change. Named events capture who/what/when/where (workstation)/old/new/why when applicable. | URS-BB-011 | `BloodBankDbContext`; `IAuditWriter` | Audit tests |
| FRS-BB-078 | Result enter, in-place update, submit-for-verification, verify, correct, and invalidate write named audit events. Opening a patient chart (`GET /api/patients/{id}`) writes `PatientAccess`. List/search does not. | URS-BB-011 | `ResultService`; `PatientService.RecordAccessAsync` | `ResultLifecycleTests` |
| FRS-BB-070 | Configuration catalogs are versioned/effective-dated where modeled and write `ConfigurationChangeHistory`. | URS-BB-012 | Admin services | Admin catalog tests |
| FRS-BB-080 | HL7 inbound stores raw message, parse status, ACK, and error-queue entries. ADT/ORM follow a merged MRN to the survivor and do not write demographics onto the loser. ADT A18/A40 apply <c>PatientMergeService</c> when configured. | URS-BB-013, URS-BB-015 | `Hl7InboundProcessor`; `PatientMergeFollow` | Phase 5 HL7 merge tests |
| FRS-BB-090 | Downtime recovery is documented; duplicate prevention uses unique keys listed in `docs/DOWNTIME_PLAN.md`. | URS-BB-014 | Downtime plan | Operational checklist |
